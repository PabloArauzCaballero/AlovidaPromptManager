# HALL-09 — El módulo `pharma_lab` existe sólo en el código: 44 tablas de deriva

**Estado de evidencia:** `VERIFIED` (medido contra el baseline construido esta noche)
**Alcance:** `mantra-core-health-model` + `mantra-core-health-api` — territorio ajeno. Se documenta.
**Consecuencia para H4:** su DoD dice «la deriva detectada **bloquea el cierre**, no es una
advertencia». H4 no puede cerrarse como `HECHO`.

## La medición

Entidades del ORM con tabla declarada, contra las tablas del baseline:

```
entidades con tabla declarada : 1166
tablas en la base             : 1201
TABLA-AUSENTE (la entidad la declara, la base no la tiene) : 44
```

## Las 44, agrupadas por causa

**36 son el módulo `pharma_lab` completo** — `pharma_labs`, `pharma_products`,
`medical_visitors`, `visit_requests`, `visit_records`, `visit_surveys`,
`regulatory_documents`, `pharmacovigilance_reports`, `material_assets`… y

**8 más son sus espejos de auditoría**: `audit.pharma_labs_history`,
`audit.pharma_products_history`, `audit.medical_visitors_history`,
`audit.visit_requests_history`, `audit.pharma_lab_staff_history`,
`audit.pharmacovigilance_reports_history`, `audit.regulatory_documents_history`,
`audit.informational_materials_history`.

**Las 5 restantes son las fantasma ya conocidas y documentadas**:
`organization_extensions.data_use_agreements`, `payments.cash_registers`,
`pharmacy_inventory.purchase_quotations`, `procedures_perioperative.instrument_sets`,
`system_ops.accepted_risks`.

## Por qué faltan las 44 de `pharma_lab`

El módulo nació en el código y **nunca llegó al modelo**:

```
src/modules/pharma_lab/                     → existe en la API
Mantra Core Health Context/modules/*pharma_lab*.puml  → NO existe (67 .puml, ninguno suyo)
SQL/*pharma_lab*                            → NO existe
grep -rl "pharma_lab" SQL/                  → 0 resultados
```

Hay `24_pharmacy` y `25_pharmacy_inventory`, que son **otros** módulos. `pharma_lab` no tiene
`.puml`, no tiene DDL, y por lo tanto no existe en ninguna base reconstruida desde `SQL/`.

## Es el mismo defecto que ya pasó, y hay precedente de cómo se cerró

Es exactamente el patrón del **módulo 64 `audio_assets`** (2026-08-12): entidades MikroORM y
catálogo de índices en el código, sin `.puml` ni una línea de DDL. Aquella vez el síntoma fue un
int-spec fallando 6/6 con `relation "audio_assets.audio_assets" does not exist`, y se cerró
**transcribiendo** al modelo lo que las entidades ya declaraban.

Acá el síntoma está latente por la misma razón que entonces: con `ORM_SCHEMA_SYNC=off` la app no
crea nada, así que la falta no se ve al arrancar — se ve cuando algo toca esas tablas.

## El riesgo concreto

Con `ORM_SCHEMA_SYNC=safe` el ORM **crearía las 44 tablas por su cuenta** en el arranque: la
dirección de cambio prohibida, y en un módulo entero. El `.env` fija `off` desde el 2026-07-30 y
por eso no ha ocurrido, pero el material para que ocurra está cargado.

## Lo informativo, que no es deriva

79 tablas están en la base y no tienen entidad (`cross_store_consistency.*`, `lakehouse.*`…).
Eso no es deriva bloqueante: son tablas que el DDL declara y que ningún módulo de la API mapea
todavía. Se registra para que nadie lo lea como error.

## Qué hay que decidir, y no es nuestro

Promover `pharma_lab` al modelo por el pipeline de las 4 capas (`.puml` → `gen_ddl.py` → `SQL/` →
entidades), como se hizo con el 64. Hasta entonces, cualquier prueba de integración que toque ese
módulo falla en base limpia, y el conteo de tablas del proyecto no cuadra con el del ORM.
